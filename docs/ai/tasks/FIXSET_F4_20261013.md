## Behavior and compatibility

Old block/preset decoding no longer claims an upgrade without a world context.
Native chunk onLoad upgrades only the main overworld/registered dungeon templates
that have no run ownership. Fixed/generated instance dimensions and all registered
run states stay compatible without advancing versions. Authentic individual block
and preset upgrade messages remain. Unknown fields, authored weighted SpawnData,
equipment and opaque preset components survive old/current repeated saves. Native
load already restores current/weighted data; onLoad no longer rewrites its entity
ID and erases authored fields.

No chunks are forced. Old/unloaded spawners migrate on their next natural main-world
load. Old named preset-file formats remain compatible reads; files advance only on
explicit save, and imported block data follows the same world boundary. After
visiting/upgrading or editing the required development chunks, the developer must
explicitly /world save dungeon_1. Old snapshots receive a bounded actionable notice,
not an instance migration. No world entry, command execution, snapshot publication
or production world-file mutation was performed by the assistant.

Untouched supported presets retain their complete raw payload, including values
unknown to the installed codecs, even after the migration version has advanced.
An explicit edit replaces its own fields and retains unrelated raw fields.
Future schemas remain opaque. Existing optional defaults remain compatible.
Backward code can read the same persistent version154/preset5 shapes, but cannot
provide this new preservation guarantee; normal backups/source rollback apply.

New hires choose from [80 verified historical names](FIXSET_F4_NAME_SOURCES_20261013.md):
eight pools of five male/five female, all distinct and at most nine letters.
The broad Asia/Africa/Mediterranean labels document their actual represented
cultures. The original 100-name UUID mapping remains frozen for legacy contracts.
Absent display_name decodes to that old name and the next save persists it;
new contracts persist their new chosen name. All other contract fields, IDs,
skins and unknown NBT remain unchanged and defensively copied. Older code ignores
display_name and may revert new names to its old mapping on rollback.

## Diagnostics and measured limits

Wolf logs are enabled for Cameron's next incident. [WolfSpawn] emits at most one
periodic summary per ten wall-clock seconds, plus a final server-stop flush.
It uses fixed event counters, two samples per event, at most16 run/dimension count
contexts, and at most256 weak pending join entries. Counts are events, not unique
wolf totals. Samples include native UUID, bond, owner, saved/current run and state,
dimension, position, role and mercenary contract identity.

Join attempts and actual native UUID-lookup-confirmed additions are distinct.
Native callbacks after canceled legacy admission are unconfirmed, never successful
spawns. Missing bounded metadata is unknown origin, never assumed fresh. Disk
reloads, eggs, births, mercenary attempts, ended/foreign runs, copied/invalid/held
bonds, hired rejection and removals are labeled. Explicit rejection clears pending
metadata. Registry context resolution occurs only for retained samples; event
counters do not scan entities, worlds, inventories or runs. No saved diagnostic
tags, packets, new dependencies, heap settings or gameplay decisions are added.
The JVM opt-out is -Dcosmicdungeon.disableWolfDiagnostics=true; default remains on.

[DungeonStartupTiming] records synchronous startup phase attempts/durations:
snapshot copy, native world opening, chunk access (cached hits/initialization/wait),
schematic file load, paste, chest binding, migration, player wolf admission,
registration, mercenary admission and teleport. A fixed enum array and one
thread-local scope emit one summary per accepted preparation attempt; no background
queue or new chunk request. Nested times overlap. Failed scopes retain measured
costs. Chunk requests unwind through finally on success or failure, excluding later
cleanup and counting subsequent requests independently; inactive requests allocate
no diagnostic supplier. Existing per-start schematic caching remains unchanged. No optimization
based solely on the earlier four5.245-15.924s backlogs/677upgrade logs/36pastes was
made, and no causal or whole-world performance claim is made.

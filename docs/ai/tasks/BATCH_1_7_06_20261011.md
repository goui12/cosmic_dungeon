## Implemented card6
- Trusted server recipe transaction API accepts server-owned predicates/output and class allowlist, never client-selected costs or outputs. Own ingredients are preferred; otherwise remaining requirements draw from eligible online YES donors in the same active D1 party regardless of distance/dimension. Crafter must be alive inside the active run. Dead/offline/spectator/Developer, exited/sealed/wrong-instance, open-container/carried-item and competing transactions are rejected.
- Fair allocation sorts ingredient keys and chooses the least-recent donor per unit, deterministic UUID ties, combining inventories with different ingredients. Donation ranks advance only after committed debits. Availability is an alternative capacity (maximum64 crafts), not a reservation. Native inventory dirty hints invalidate on-demand snapshots; a five-tick maximum cached age catches missed hints. Execution always copies live inventories; no global inventory tick scan.
- Exact native before/after inventory images retain authored components and untouched slots. Output capacity is checked before reservations, using native identical-component stack limits and hotbar preference. One pending craft/run/owner serializes clicks. Membership, consent, alive/online state, source images and metric ordering are checked again after all reservations and immediately before the durable commit.
- Donors receive the requested contribution message with quantity after verified owner save. Shared use/contribution and separate own-use totals appear in party inspection. Donor rank and resource-event identities use the same transaction, not a second independent counter.
- Shared inventory/recovery guards, login, death, pickup, dimension/logout cache invalidation, and cleanup/reset integration prevent unresolved custody from being silently overwritten. Cleanup waits for crafting resource projection before freezing terminal run totals.

## Persistence and recovery
New cosmicdungeon_shared_crafts_v1 world SavedData and shared_craft_reservation_v1/shared_craft_receipt_v1 player ClassData keys are additive. Existing root fields and full native item components survive. New journal schema1 preserves unknown NBT fields and rejects future/malformed shapes. Existing worlds without these keys start empty; no spawner, recipe, item ID or authored-chest migration.

Protocol: durable PREPARED world decision; exact reservation in each native player save; fresh revalidation; durable COMMITTED decision; per-owner inventory afterimage plus bounded receipt; verified owner acknowledgement; resource projection; metrics acknowledgement; verified retirement. PREPARED recovery cancels without consumption. COMMITTED recovery completes the already-authorized decision even if consent later changes. Native owner receipt suppresses repeated debit/output. Uncertain save/journal state retains custody, logs and disconnects affected owners for recovery; it never invents a rollback after a committed output. Offline owners keep the journal pending until they return. Do not delete journals or downgrade while custody is pending.

Dungeon Instance Metrics gains two independent version1 XML schemas:
- resources/<instance-UUID>/<transaction-UUID>.xml: immutable exact item/quantity, donor/recipient, skill, own/shared and timestamp events. Full history is segmented, so long runs have no fixed craft-count cap.
- resource-state/<instance-UUID>.xml: atomic exact resource afterimage with transaction sequence, donor order, own/shared/contributed counters and latest64 resource events. Segment then afterimage are written before SavedData projection. On restart the afterimage restores counters and sequence together; retries cannot double-add metrics.
The existing run/totals schema stays compatible. Canonical instance XML includes recent64 events and shared aggregate counters; complete own/shared event detail remains in segments and state. Finalized player/server totals use existing shared used/contributed maps. Offline rebuild copies finalized resource state/history alongside reconstructed totals. Unknown/future XML, missing identity, conflicting transaction contents, malformed counters and unsupported atomic replacement fail closed with original files retained.

Notifications suppress ordinary replay using the owner receipt. A process crash after that receipt and before chat delivery may omit the message; exactly-once inventory/metrics does not promise reliable chat delivery. Storage durability depends on the filesystem honoring forced writes/atomic replacement; no portable directory-fsync guarantee is claimed.

## Bounds and performance
At most6 owners,16 ingredient kinds,64 consumed units/craft,32 pending journals,4MiB/plan; one pending decision per run/owner. Native player saves reuse existing64MiB bounded proof. Resource segments <=64KiB, exact state <=2MiB,512 distinct item IDs per owner/category, recent64 events. Counters/sequence overflow is rejected before committing inventory. Completed transaction files grow with actual crafts; no archive-wide runtime scan. Context caches track live runs/players only. No new threads, heap flags, dependencies or network packets.
Verified synchronous saves/atomic writes are deliberately per craft, not per preview/tick. They can add click latency and need live server profiling; pure six-member/64-item codec timing and size are captured by regression output, not presented as production TPS. Future recipes must preserve conservation if batching disk work is considered.
